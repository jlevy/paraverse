# Feature: Knowledge Base Browser

**Date:** 2026-10-24 (last updated 2026-10-24)

**Author:** Claude Code session, for Joshua Levy

**Status:** Implemented

> The GitHub Universe KB and its pipeline now live in their own repository,
> [jlevy/universe2026-md](https://github.com/jlevy/universe2026-md), which Paraverse
> mounts as a git submodule at `vendor/universe2026-md/`. Paths under `kb/` in this
> document refer to `vendor/universe2026-md/kb/`, and the crawler’s files are in that
> repository’s `pipeline/`.

## Overview

A clean, consistent, read-only administrative browser for the whole conference knowledge
base, served from FalkorDB. Every kind of entity (sessions, people, profiles,
organizations, repositories, accounts, rooms, taxonomy terms, pages, ...) gets the same
kind of table, with sorting, filtering and paging.
Every record gets the same detail view.
Every reference is a link with a hover preview, and relationships link the tables to
each other.

It is one small component:

- a Python server (Starlette and uvicorn, following metabrowser) with a JSON API and
  server-sent events
- a no-build static front end (vanilla ES modules and CSS, following tbd’s web viewer)

It loads fast and embeds anywhere: a browser tab, a WebKit web view, or an iframe.

It builds on the FalkorDB spike in `db/`
([spike spec](plan-2026-10-24-conference-kb-in-falkordb.md)) and replaces its first
explorer page. The KB itself is described in
[the knowledge base plan](https://github.com/jlevy/universe2026-md/blob/main/docs/project/specs/done/plan-2026-10-24-universe-knowledge-base.md).

## Goals

- **Show everything.** Every node kind and every field of every record is reachable.
  Nested values (time slots, affiliations, claims and their evidence, sponsorship,
  sources) are rendered, not hidden in JSON.
- **One generic, schema-driven model.** Table columns, field order, labels,
  descriptions, nested shapes and reference targets come from the KB’s own compiled
  softschema JSON Schemas and from the graph.
  There is no per-kind UI code beyond a small table of default columns.
  A new kind or field appears with no front-end change.
- **Relational navigation.**
  - References are link chips with hover popovers.
  - Each record lists its outgoing and incoming relationships, grouped by type.
  - Each table can be filtered by a relationship, for example “sessions presented by
    person X” or “sessions about term Y”.
- **Clean, simple, consistent visuals.** One small design vocabulary (tokens, table,
  chip, card, popover, badge) borrowed from tbd’s web viewer and metabrowser, light and
  dark.
- **Easy to load and embed.** No build step and no CDN at runtime.
  Deep-linkable URLs. An embed mode without chrome for the app.
- **Live.** When the graph is reloaded, open browsers are told over server-sent events
  and refresh the current view.
- **Review built in.** Data-quality checks from the KB review run as named queries and
  appear as a Review table whose rows link to the entities.

## Non-Goals

- Editing data. The KB is generated by the crawler; corrections go into the curation in
  [universe2026-md](https://github.com/jlevy/universe2026-md) (`pipeline/curation/`) and
  a rebuild. The browser stays read-only.
- Authentication, multi-user hosting or public deployment.
  The server binds to loopback.
- Replacing the named query catalog.
  The browser and other clients share `paraverse_graph`, its graph and its named
  queries.
- A graph-drawing view as a primary surface.
  A neighborhood graph may stay as an optional tab, loaded only when opened.

## Background

The KB covers four editions, 2023 to 2026. It has 5,834 nodes in 18 kinds and 26,380
relationships in 44 types.
Every artifact validates against its compiled schema (`universe-kb validate`), and the
crawler’s 97 tests pass.

The `db/` spike already loads the KB into FalkorDB in about 2 s, with staging, count
checks, a swap and a unique constraint.
It stores every payload as `doc`, plus flattened properties and indexes, and it has a
15-query read-only catalog.

The compiled schemas (`kb/_schemas/*.schema.yaml`) give each kind’s:

- title and description
- required fields
- `$defs` for nested shapes (`TimeSlot`, `SessionSpeaker`, `Affiliation`, `Claim`,
  `Evidence`, `Source`, ...)
- a typed-ID `pattern` on every reference field, which names the target kind (for
  example `^(event):...` or `^(gh|acct):...`)

That is enough to render any record generically.

## Design

### Architecture

```text
vendor/universe2026-md/kb/ ──paraverse-graph load──►  FalkorDB graph `universe`
  artifacts, _graph/, _schemas/                       entity nodes and relationships
                                                      (:Schema) nodes (one per kind)
                                                      (:GraphMeta) node, after load: PUBLISH paraverse-graph:<graph>
                                                              │
                     paraverse_graph.browser (Starlette app, uvicorn) ◄┘
                       /api/meta /api/schema/<kind> /api/rows/<kind>
                       /api/entity/<id> /api/card/<id> /api/search
                       /api/review[/<check>] /api/query/<name> /api/events (SSE)
                       /  and  /static/*   (no-build ES modules and CSS)
                                                              │
                     browser tab · WebKit web view (embed=1) · iframe
```

All data comes from FalkorDB at request time.
The server reads nothing from `kb/` directly, so the same server works against a remote
FalkorDB loaded elsewhere.

### Data in FalkorDB

Everything the browser shows is stored in FalkorDB:

- **Entities and relationships,** as the spike stores them.
- **One `(:Schema)` node per kind:** `kind`, `label`, `title`, `description`,
  `contract`, `json` (the compiled JSON Schema), and `fields_json`, a flattened field
  list. Each field has name, title, description, JSON type, whether it is required,
  whether it is a reference and to which kinds, and a nested `$def` name if any.
  The loader derives it once from `kb/_schemas/`. Kinds with no schema of their own
  (`day` and `term`, which are nested in `event` and `facet`) take their field list from
  the parent’s `$defs`.
- **`(:GraphMeta)`:** as today, plus relationship statistics (`kind -[TYPE]-> kind` with
  counts), so the API can describe relationship columns without scanning the graph per
  request.
- **Live updates.** After a successful swap, the loader runs
  `PUBLISH paraverse-graph:<graph> {"type":"graph.loaded", kb_digest, loaded_at}`.
  Because FalkorDB is Redis, live updates need no extra infrastructure.

### API

Every endpoint is a read-only JSON GET. Labels, relationship types and property names
are interpolated into Cypher only after they are checked against the `Schema` nodes,
`LABELS`, the stored relationship statistics and a strict identifier pattern.
Values are always query parameters.
Every query runs with `GRAPH.RO_QUERY` and a timeout.

As built:

| Endpoint | Returns |
| --- | --- |
| `GET /api/meta` | `{graph, kb_digest, loaded_at, node_total, edge_total, groups: [{title, kinds: [{kind, label, title, description, count}]}], relationships: {TYPE: count}}` |
| `GET /api/schema/<kind>` | `{kind, label, title, description, contract, fields, defs, computed, default_columns, relationships: [{name, direction, type, kinds, count}]}`. Each field is `{name, title, description, type, list, required, ref_kinds?, def?, enum?, format?}`. |
| `GET /api/rows/<kind>?offset&limit&sort&order&q&cols&rel=<in\|out>:<TYPE>:<id>&f.<field>=<value>` | `{kind, columns, total, offset, limit, sort, order, rows: [{id, name, cells}]}`. A cell is one of: a scalar or list; `{refs: [{id, name, kind}]}` for references; `{nested, count, preview}` for nested shapes; `{items: [{id, name, kind}], count}` for relationship columns. |
| `GET /api/entity/<id>` | `{id, kind, name, labels, kb_path, doc, properties, refs: {id: {name, kind}}, relationships: {out, in}}`. Each relationship group is `{type, count (links), distinct (entities), items}` with up to 50 items `{id, name, kind, edge}`. Sources are in `doc.sources`. |
| `GET /api/card/<id>` | `{id, kind, name, labels, title, image, fields: [{name, value}]}` |
| `GET /api/search?q&kinds&limit` | `{q, hits: [{id, kind, name, snippet, score}]}` from the full-text index on `Entity.search_text`. User text is sanitized for the search syntax. |
| `GET /api/review`, `GET /api/review/<check>` | `{checks: [{name, title, severity, area, description, count, truncated}]}`, sorted by severity, then area. One check adds `rows: [{id, name, detail}]`. Results are cached per graph load. |
| `GET /api/query/<name>` | The named-query catalog shared with the CLI and other clients |
| `GET /api/events` | SSE: `hello` on connect, `graph.loaded` after each reload, `resync` after overflow, and heartbeat comments |

- **Paging** is server-side, with a default `limit` of 100 and a maximum of 2,000. The
  browser asks for 2,000 rows, so every current kind fits on one page (the largest,
  repositories, has 1,286 rows: about 300 KB and 50 ms from the API, and about 300 ms to
  render). The pager only appears beyond 2,000 rows.
- **Table search.** `q` within a table is a case-insensitive substring match on
  `search_text`, which is predictable for an admin filter.
  Global search uses the full-text index.
- **`f.<field>`** filters on equality for scalars and on membership for lists.
  Reference and nested fields are filtered through `rel=` instead.
- **`rel=`** filters by a linked entity.
  `in:PRESENTS:person:x` returns the sessions that person:x presents.
- **Errors** are JSON `{error}`: 400 for bad input, 404 for unknown ids and routes, 503
  for an unloaded graph or a query timeout.
  A foreign Host header gets 421.

### Front End

Plain ES modules and CSS served from `paraverse_graph/web/`, with no bundler, no npm
runtime dependency and no CDN.

- **Shell.** A sidebar lists kinds grouped as Program, People, Organizations, Code,
  Content and Taxonomy, with counts.
  Top bar: global search, and a KB digest and load-time badge that flashes on
  `graph.loaded`. A Review link.

- **Routing** uses the URL hash, so links are deep and the app can open any view:
  - `#/t/<kind>?sort=&order=&q=&rel=&f.x=` for a table
  - `#/e/<id>` for a record
  - `#/review` and `#/review/<check>` for review checks
  - `#/search?q=` for search

- **Table view.** Sticky header, sortable columns, a column picker (any schema field or
  relationship column), a filter box, chips for active relationship filters, and paging.
  Cells render by type:
  - text and numbers
  - booleans as badges
  - URLs as external links
  - images as small thumbnails
  - references as entity chips
  - relationship columns as up to three chips plus “+N”

  Clicking a row opens the record.

- **Record view.** A header with name, kind badge, `id`, labels and the source path.
  Then:
  - **Fields** in schema order.
    Nested objects render as a definition list; lists of objects render as a sub-table
    using the `$def`’s fields; references render as chips; long text renders as Markdown
    (escaped, with links only).
  - **Relationships:** outgoing and incoming, one compact table per type, each with a
    “show all in table” link to `#/t/<kind>?rel=...`.
  - **Sources** with links.
  - **Raw:** the payload as JSON, and the KB path.

- **Popovers.** Hovering or focusing any entity chip shows `/api/card/<id>` in a
  popover, cached per session.
  Clicking navigates.

- **Embed mode.** `?embed=1` hides the sidebar and top bar, keeps the routes, and posts
  `{type: "paraverse-kb:navigate", id}` to `window.parent` (iframe) or a WebKit message
  handler when one exists, so the app can react.

- **Theme.** CSS custom properties with light and dark through `prefers-color-scheme`,
  overridable with `data-theme`.

### Server and Project Setup

- **Server.** `paraverse_graph.browser.create_app(graph, ...)` returns a Starlette app,
  run with uvicorn by `paraverse-graph serve`, which binds to 127.0.0.1 and checks the
  Host header. The existing stdlib server is removed.
  - **SSE** follows metabrowser’s events route: one Redis pub/sub subscriber task per
    process fans out to per-client queues, with a heartbeat and disconnect handling.
  - **`--watch`** (optional) watches `kb/_graph/stats.json` with watchfiles, reloads the
    graph, and the publish reaches every client.
- **Project.** It stays the `db/` uv project (simple-modern-uv setup; 14-day cool-off).
  New dependencies are Starlette, uvicorn and watchfiles, plus httpx for tests.
  Optional JS linting follows whichever of tbd or metabrowser the borrow review
  recommends, without adding a build step.

### Borrowing From tbd and Metabrowser

Both repositories belong to the project’s maintainer.

- **tbd:** MIT.
- **metabrowser:** AGPL-3.0, relicensed by its author for use here.

Borrowed blocks carry a one-line provenance comment.
The rule is to take focused pieces, never an app’s coupled modules.

| Piece | Decision | Source |
| --- | --- | --- |
| Design tokens, type scale (15/14/12 px), radii, light and dark, scrollbars, reduced motion | tbd | `packages/tbd/src/web/styles.css`: the rules doc, `:root` tokens, dark remap. Bead-specific roles are dropped. |
| Table chrome: sticky header, sort buttons and indicator, row hover, pager, empty state | tbd CSS, fresh JS | tbd `styles.css` table rules. One generic renderer is written fresh. |
| Tags, pills, tooltips, copy button, theme menu, relative times | tbd | `styles.css` and `client.ts` (tooltip, copy, theme), and `core.ts` `formatRelativeAge` |
| Facet filter chips | metabrowser | `static/filter-controls.js` and its `.chip*` CSS, with the `window.metabrowser` hook replaced by an export |
| Search palette look and ARIA combobox markup; `.kbd` key hints; modal look | metabrowser CSS, fresh JS | `.search-palette-*`, `.kbd`, `.modal-*` CSS. The JS is written fresh around `/api/search`. |
| Icons | metabrowser format | `static/icons.js` (Lucide), trimmed to about 10 glyphs |
| EventSource reconnect and backoff | metabrowser | The reconnect, backoff and stable-reset block in `static/app.js` |
| Router, record view, hover-card popovers, keyboard handling | fresh | Neither repo has generic versions of these. |
| Server: app factory, Host validation, compact JSON, bounded query parameters, SSE bus and heartbeat, quiet uvicorn launch | metabrowser patterns | `server.py` (Host middleware, JSON response, `_query_*` helpers), `events_route.py` (`_EventBus`, stream loop), `cli/serve.py`. Inventory, plugins, ring buffer and snapshots are dropped. |
| Live-update source | fresh | Redis pub/sub from the loader (FalkorDB is Redis), plus optional watchfiles on `kb/_graph/stats.json` |

The front end avoids metabrowser’s KPress fonts and tbd’s single-file stitch build.
It uses system fonts and a few static files.
tbd’s test that “no color literals appear outside `:root`” is ported as a pytest.

### Review Checks

The three KB reviewers (people, program, organizations) each return reusable read-only
checks that produce `id`, `name` and `detail`. They are curated into
`paraverse_graph/review.py`, with name, title, severity, description and Cypher.
They run read-only through the API and appear in `#/review` with counts and a severity
badge. Their findings become beads against the crawler.

## Testing Strategy

- **API (pytest, real KB in a temporary embedded FalkorDB):**
  - every kind has a `Schema` and a non-empty first page
  - `total` equals the kind’s count
  - sort and paging are stable
  - `rel=` filters return only linked rows
  - every reference in `entity` resolves to an existing node
  - `card` exists for every kind
  - `search` finds a known title
  - unknown kinds and fields return 400
  - a foreign Host header returns 421
- **Review:** every check runs and returns the three columns.
- **SSE:** a `PUBLISH` reaches a connected client within a timeout.
- **Front end:** a scripted pass in a real browser over every kind’s table and a sample
  record per kind, with no console errors.
  Popovers, deep links, embed mode and dark mode are checked.
- **Existing:** the spike’s tests and the Swift decoding sketch stay green.


Then open <http://127.0.0.1:8766/>.
